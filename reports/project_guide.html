The problem, in plain language

Start here. Everything else in this document serves this one paragraph.

Some people with paralysis have a small array of electrodes implanted in the motor cortex. Software called a decoder reads the electrical activity and turns it into cursor movement, so they can use a computer by thinking about moving.

Over months, the recording gets worse. Electrodes drift, individual neurons drop out, the electrical relationship between brain and machine shifts. The decoder was trained on how the signal looked then, and it keeps confidently producing output based on a signal that no longer matches.

Eventually the cursor stops obeying and someone has to stop everything and retrain the system — recalibration. It is slow, it interrupts the person's day, and today it happens on a fixed schedule or after something has already broken.

The gap this project fills

Nobody is watching the input. The field has spent a decade building better ways to correct drift, and almost no effort on noticing it early enough to act. There is no standard way to even test whether such a warning system works.

So: build the thing that watches, and build the test that proves whether watching works.

Why it matters — and the honest weak spot

Stated with its problem first, because a judge will find the problem anyway.

The weakness, said plainly

Very few people currently use implanted brain-computer interfaces — on the order of dozens worldwide. If the project's whole claim is "this helps those people," that is a thin claim. Verify the real figures yourself and cite them; do not take this number on trust.

But that is not actually the scope of the problem. The real failure mode is more general:

A machine-learning model runs on a sensor that slowly degrades, and nobody watches the sensor. The model keeps producing confident output long after its input stopped being trustworthy.

That is not a brain-implant problem. It is a continuous-glucose-monitor problem, a myoelectric-prosthesis problem, a wearable-heart-monitor problem. Those user populations are in the millions.

And the claim is earnable rather than rhetorical: the monitor reads channels × activity over time, which describes all of those signals. It can be tested on a second modality using public, de-identified datasets — no participants, no permissions, no risk.

Everything done so far

In order. The numbering is real chronology, not decoration — each phase depended on the one before it.

P0

Get the data and understand itdone

Found a public dataset: two people with implants, using a BCI over months while it degraded. About 9 GB. Written a program that downloads it automatically and checks each file's fingerprint, so anyone can repeat it exactly.

Then catalogued it — every file, every column, what each number means. Each fact labelled either checked in the data, stated by the paper, or my guess, so those never get confused.

P1

Prove the code can be trusteddone

Before doing anything new, we re-computed a result the original scientists had already published, to see whether we would get their number.

They got 0.985. We got 0.985. That means the pipeline works and the data is being read correctly. Without this, everything downstream would be unverifiable.

P2

Run the original test — and report that it faileddone

The original idea came from early-warning signal theory: systems approaching a tipping point get twitchier and slower to recover, and you can measure that.

We wrote down exactly what would be tested and what would count as success, locked it in a timestamped file, and ran it once. The number came back "statistically significant" — which normally means you found something.

It was wrong, and we caught it, because we had also written down one check in advance: is the warning signal quiet when the person is doing fine? It was not. It climbed steeply during weeks when performance was 93–100%.

P2b

Work out why it faileddone

Three findings, each independently confirming the same thing:

The elaborate warning signal was mostly just how much brain activity there is, which drops 56% across the recording. Simply counting activity predicted performance just as well as the whole five-step method. And the signal read almost the same whether the person was doing the cursor task or browsing the web — so it was measuring the electrodes, not the person.

Out of that came the rule the whole project now rests on:

The rule this bought

A warning light that is on when nothing is wrong is not a warning light. Any candidate signal must first prove it stays quiet during healthy operation. That check comes before any other result is even looked at.

The turning point

Why the project changed shape, and why the change was necessary rather than optional.

Think about grading a fire alarm. To know whether it went off early enough, you need to know when the fire started.

In this dataset, nobody wrote that down. We only see the damage afterwards and guess backwards. So "the warning came 12 days early" really means "12 days before the moment we decided to call it a fire." Change the definition, change the answer. That is circular, and no amount of statistical care fixes it — we were careful, and it did not.

It is worse than that: you cannot count false alarms either, because that needs a long stretch you know was fine with nothing coming, and the data cannot supply one.

The consequence

Early-warning time and false-alarm rate are the only two numbers that decide whether a warning system is worth having. Neither is measurable from data you merely found. They become measurable the moment you cause the problem yourself, at a time you wrote down first.

That is why this project generates its own data. Not because a competition wants originality — because the central claim is uncheckable without it.

What is actually being built

No hardware. Nothing worn by anyone. Nothing attached to a real BCI.

The deliverable is a program that runs live. It sits beside the decoder and reads the same incoming signal the decoder reads — but never sees the decoder's output, and never sees the task. It branches off before the decoder:

neural signal ──┬──→ decoder ──→ cursor moves │ └──→ decoder-guard ──→ risk · state · reason

This is why the decoder does not need to be good, or even finished. The monitor does not look at it. Every update, the monitor outputs four things:

OutputWhat it is
Risk scoreA number from 0 to 1 — how far today's signal has moved from healthy
Warning stateOne of four levels, so it reads at a glance
ReasonWhich kind of problem is driving the risk — the part that makes it actionable
ConfidenceHow sure it is. Low confidence is reported, not hidden
NOMINAL
Signal matches healthy. Nothing to do.
WATCH
Something is moving. Not yet actionable.
WARN
Schedule a recalibration soon.
FAIL-LIKELY
Do not trust the decoder's output.

The demonstration a judge watches

A laptop replays recorded neural data at real speed, like playing a video. It streams into the monitor. On screen: the risk score moving, the status light stepping up, and a line of text saying why. At some point the software says WARN. Some seconds later, the cursor performance visibly falls apart.

The warning came first — and you can state exactly how early, because you chose when to break it.

Why "no reason given" is a design failure

"Recalibrate", "the electrode is failing", and "nothing is wrong, the person is just doing something different" are three completely different responses. A monitor that cannot tell them apart is not usable, no matter how good its accuracy number is.

Phase 3 — what is built and what is next

Deliberate order: the grading system gets built before the thing being graded, so the grading cannot be bent to fit.

3.1

The fault injectordone

Deliberately breaks a copy of the real recorded data, at a moment chosen and written to disk beforehand. 1,073 test cases. Original files are never touched. Re-drawing the schedule is refused unless a written reason is recorded — so a start time cannot be moved after seeing how the monitor did.

Four kinds of breakage, chosen to span one axis: how visible each is to the crude method of simply counting activity. If every fault were the obvious kind, "beat the simple method" would be a formality rather than a test.

3.2

The reference decoderdone

Exists only to grade — it turns a broken signal into a performance number, so "the warning came before performance dropped" becomes checkable. It needs to beat chance and never change; beyond that, accuracy is not a goal.

It gets 54.6° of error on held-out healthy data against 90.7° for chance. Good enough, and frozen.

3.3

The grading systemdone

How early the warning came, how often it cries wolf, and the five pass/fail gates — including the silence gate. Built before the monitor exists, on purpose.

3.4

Score the simple methods firstdone

Run three crude baselines through the grading system, so the bar to beat is known before there is anything invested in clearing it.

3.5

Build decoder-guarddone

Learn what healthy looks like — from healthy data only, never seeing a failure label. Then score risk, run the state machine, and add the reason-giving.

3.6

Second signal typerecommended next

Run the same code, unchanged, on a public dataset of a different kind. This is what turns the broad impact claim into a demonstration.

Something worth knowing: the calibration caught four real bugs

Before the corpus could be trusted, each kind of breakage had to be checked against the decoder. That check found four errors that would each have quietly corrupted the final results — a severity ladder that ran backwards, a fault type that was supposed to be invisible to activity-counting but raised activity by 116%, and a start-time guarantee that held only by floating-point luck.

Kind of breakageEffect on total activityMeaning
Overall signal loss−48%The easy case. Counting activity catches it.
Electrodes dying−54%Partly visible
Channels drifting apart−2%Wrecks decoding while invisible to counting
Signal geometry rotating−18%Only bites when large — a stated limitation

The third row is the important one. It is the case that makes "is your method better than just counting?" a genuine question.

What actually went wrong — and it is not what you would guess

The problem is not that nothing can detect the faults. Five configurations warned early, and one of them warned by nearly a minute:

The best single number so far

On participant T5, the robust-dispersion measure reached a median lead time of +57.5 seconds (95% confidence interval 2.5 to 82.5). It genuinely warned before performance fell.

It also cried wolf nine times more often than the budget allows.

That is the real finding. The constraint is not detection, it is specificity. The risk signal is never quiet when the system is healthy — so any threshold sensitive enough to catch a fault early also fires constantly on a perfectly good recording. The one configuration that stayed within the false-alarm budget did so by barely firing at all, and its lead time was negative.

The closest anything came to the silence gate: 31% of healthy stretches still showed a rising trend, against a 10% requirement.

Why the signal is never quiet

Because the neural recording changes constantly for reasons that have nothing to do with failure. Within a single five-minute block, overall activity drifts about 15%. Across the 142-day record, mean activity falls 56.5%. Those changes are comparable in size to the injected faults. The monitor is not wrong to notice them — they are real. They are just not failures.

A planned fix that failed, reported as a result

Back in August the project wrote down, in advance, that the drift should be removed by fitting a trend line and subtracting it. That was run. It made things worse — on T5 the silence gate went from 63% to 81% of healthy stretches trending.

The reason is worth understanding: a line fitted on the past and extended forward drifts further from the truth the further out it goes. So on drift that is not exactly straight, subtracting the line adds a trend at the far end. Removing a trend properly requires seeing the whole recording — which a live monitor, by definition, cannot do.

Comparing each moment against a short sliding window of the recent past is the only approach that helped, roughly halving the failure rate. It still did not come close to passing.

This failure is recorded rather than quietly swapped out. It was written down first, it was run, and it did not work — which is the entire reason for writing things down first.

So is the project in trouble?

No — but the deliverable is now clearly the one that was always the more valuable half.

The project was deliberately built so that this outcome would still be worth reporting, and Phase 2 already proved it would actually be reported rather than buried. What exists now:

ContributionWhy it stands regardless of the monitor's score
A benchmark that did not exist1,850 fault episodes across two participants with known start times — the ground truth nobody previously had
A test batteryFive gates in a fixed order, silence first, so a detector cannot be praised for a trend that was there all along
Systematic evidenceThe published measure, a trivial baseline, and a purpose-built monitor all fail — measured, not asserted
A diagnosisWhy they fail: the signal moves constantly, at a scale comparable to real faults

Put plainly: "here is a way to test whether a decoder-health monitor works, and here is evidence that the current generation of them does not" is a stronger and more honest contribution than a fragile positive result would have been.

Limitations, stated up front

Injected episodes are evaluated open-loop — no live person adapting. Only two participants, and they disagree. One fault type stops being a clean test at high severity. Attribution names only three of its four possible causes, meaning it is partly collapsing onto whatever is chronically lit.

Open decisions — yours

None of these should be settled by asking which choice would make the results look better.

Add a second signal type?

Recommended: yes. It is the difference between "this might generalise" and "here is it generalising." Public data, no participants, no risk.

Two kinds of breakage, or four?

Four is designed and built. Two would be faster and is defensible. Four is already working, so there is little reason to cut unless time gets short.

Is the recalibration-savings result in scope this year?

This is the headline claim — fewer recalibrations for the same performance. It is also the last thing built. Decide after the grading system reports.

Hardware rig

Dropped. It was optional, and it adds cost and risk for a capability the software path already covers. The project is now purely software.

Every term, defined

Nothing here assumes prior knowledge. Open what you need.

Decoder

The software that turns brain activity into cursor movement. It learns a mapping once, then applies it. When the brain signal changes but the mapping does not, output quality falls.

Recalibration

Retraining the decoder on fresh data so it matches the current signal. It works, but it costs the user time and interrupts what they were doing — which is why doing it only when needed is worth something.

Fault injection

Deliberately breaking something to see whether your detector notices. Standard engineering practice — Netflix runs a tool that randomly kills their own servers to prove the system survives. Here it means editing numbers in a copy of a data file. Nothing is injected into a person.

Ground truth

The right answer, known independently of whatever you are testing. Here it means knowing exactly when the problem started — which is only knowable if you caused it.

Lead time

How long before the failure the warning arrived. Meaningless unless you know when the failure actually began, which is the entire reason this project generates its own data.

False-alarm rate

How often the monitor cries wolf during healthy operation. A detector with a great lead time and a terrible false-alarm rate is useless — people stop believing it.

The silence gate

The requirement that a monitor stays quiet while the system is healthy. This project's first attempt failed it, which is why the whole approach changed. It is checked first, before any other result is interpreted.

Freezing / preregistration

Writing down exactly what you will test and what counts as success, and locking that file with a timestamp and a fingerprint, before looking at any result. It is what stops you from unconsciously picking whichever analysis looked best afterwards.

Baseline / trivial comparator

The simplest method that could possibly work — here, just counting how much activity there is. If an elaborate method cannot beat it, the elaborate method has added nothing. In Phase 2, counting activity matched the whole pipeline.

Open-loop vs closed-loop

Closed-loop means a real person sees the cursor and adjusts. Open-loop means replaying a recording, which cannot adjust. Injected faults are evaluated open-loop, so the performance number is "how wrong the decoder would have been" rather than "how badly the task went." This is a stated limitation.

Angular error

The angle between where the decoder pointed and where the person meant to go. 0° is perfect; 90° is chance; 180° is exactly backwards. It is the performance measure used throughout.

Data leakage

Accidentally letting information from the test set influence the model, which makes results look far better than they are. Prevented here by fitting only on healthy data, splitting by session, and opening the test set exactly once.

The one-sentence version

Build the thing that notices a brain-computer interface is failing before it fails — and, because nobody could previously prove such a thing works, build the test that proves it.
